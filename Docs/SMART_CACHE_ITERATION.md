## 行为与调用链

- 性能设置只保留“记录性能诊断”和 Everything；智能缓存准备自动运行。旧 `ScanWarmupEnabled` 设置仍兼容读取，但不再决定运行行为。
- 启动异步读取 SQLite 中最后显示的会话和有效计划，先恢复列表，再后台校验。恢复期间可以浏览、筛选；完成校验前整理操作保持禁用。没有缓存时维持正常扫描入口。
- 保留作者公共索引的后台初始化，删除原预热服务重复维护的完整源快照和无实际准备工作的后台任务。持久源索引提供器成为文件发现结果的唯一所有者。
- 同一上下文的并发发现串行共享完成结果，等待支持取消。监控从发现开始前建立；变化版本按源目录及扫描范围隔离，避免其他目录的变化使当前结果失效。
- 无变化复用逐文件计划；新增文件进入识别，删除文件移出列表。仅大小或修改时间变化时更新必要元数据，保留作者和人工确认字段。标签规则变化按版本使相关解析和计划失效，不删除文件索引。
- 有效内存计划覆盖会话时跳过数据库计划重读；全部有效时不重写计划。会话行写入复用预编译语句，必要计划写入移到后台。
- 列表保留未变化的行，增量更新变化记录，尽可能保留选中项和滚动位置；状态筛选存入用户设置。沿用现有排序逻辑，没有增加独立排序设置。
- 过期任务完成时核对上下文，不能覆盖最新扫描条件；关闭窗口取消扫描并在后台任务退出后释放资源。
- Everything 冷索引可能短暂漏报新文件。启动发现增加仅文件名的完整性核对，缺项时使用文件系统提供器，不重复查询 Everything。监控发现已变化时直接使用文件系统校验；缓存数据库自身及无关文件事件不会触发重复校验。
- 界面展示使用已取得的元数据，避免逐行再次探测磁盘；实际执行整理仍检查源文件和目标安全条件。监控负责失效标记；后台验证由启动、扫描或上下文变化触发，没有加入空闲定时全量扫描。

## 缓存兼容与诊断

统一使用原 `Cache/FileIndexCache.db`；沿用已有 schema 9，将模型默认值与实际版本对齐，没有新增完整扫描快照或重复表。旧版本未记录 `DisplayedSession` 时，仍需成功扫描一次建立恢复入口。

历史 `ScanWarmupSnapshot.json` 当前没有读写依赖；停止启动时删除该文件，旧字节保留，不臆测迁移未知历史格式。正常有效数据库和设置不强制重建。

SQLite 明确报告损坏或非数据库格式时，关闭连接，将原数据库及对应日志文件保存在同目录 `.corrupt-时间-标识` 备份后重建；备份失败回退已移动文件。权限或普通 I/O 错误不当作损坏处理。释放后的数据库对象不能被晚到任务重新打开。

保留 GL4 诊断格式，追加可选字段：列表恢复、首次可交互、后台校验、Everything 实际查询次数、实际识别文件数。旧历史缺少这些字段时显示“—”，明确记录的 0 保持为 0。各阶段可能重叠，不能把阶段耗时直接相加。

## 11:41 实际库反馈后的追加迭代

用户实际库首次扫描：8,490 文件，总响应 68,859 ms，其中文件提供器查询 60,900 ms、识别 7,255 ms。重启后全部计划复用、实际识别 0，校验 2,382 ms，其中提供器查询 1,812 ms。现有“提供器查询”包含 SDK 准备、IPC 等待、结果读取、完整性核对及可能的回退，因此不能凭此确认 60 秒就是 IPC 或下载等待。

本轮改用 Everything 免费的名称排序获取结果，再按 SDK 返回的修改时间在内存稳定排序，保留最新文件优先和数量截取行为，不逐文件读取磁盘时间。避免依赖 Everything 是否配置修改时间快速排序；参考 [Everything_SetSort 官方说明](https://www.voidtools.com/support/everything/sdk/everything_setsort/)。缺少 SDK 时的官方下载增加请求及读写超时（各 5 秒）；这是下载超时，不是 IPC 查询超时。

诊断追加 SDK 准备、Everything 查询等待、结果读取与排序、文件清单完整性检查四项；沿用 GL4 可选字段 SP/EW/ER/DC。旧记录显示“—”，缓存直接命中不会复用历史查询耗时。分段耗时保留到发现回退和会话克隆路径。

验证：增量契约、新增无磁盘时间读取排序测试、分段诊断历史兼容测试及真实 WinForms Everything 启动恢复测试通过；四份语言包各 1,111 键、770 引用。测试目录首次扫描 4,064 ms；重启恢复 242 ms、首次可交互 482 ms、后台校验 1,038 ms、一次 Everything 查询、8,490 缓存复用。测试环境没有复现实际库 60 秒等待，不能将上述数字作为实际库改善结论；需要实际库新诊断确定剩余瓶颈。交付程序仍为独立的 `GuiGui.CacheRecovery.exe`，不删除用户缓存。

## 11:50 重启反馈后的追加迭代

实际库新日志：首次扫描 9,741 ms；重启后台校验 2,325 ms，完整性检查 1,122 ms，窗口启动至列表可交互 1,804 ms。此次针对完整性核对与列表恢复前的工作修正。

- 文件名核对改用 Windows `FindFirstFileExW` 的 Basic 信息与 Large Fetch 缓冲，每个目录一次枚举，同时取得文件和子目录；仅为匹配扩展名构造路径，直接移除 SDK 名称集合中的对应项。发现 SDK 漏项立即停止核对并回退文件系统，避免再遍历剩余名称。仍完整验证无变化目录的全部匹配名称，不使用目录时间戳猜测“不变”，不增加新快照文件。权限/I/O 不确定时保留索引结果，取消和提前退出释放枚举句柄；不支持批量标志的提供器回退标准枚举。依据 [Windows 官方接口说明](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-findfirstfileexw)。
- 恢复旧计划与就绪状态发布不再遍历目标作者目录生成目标指纹。正常扫描、完成后的上下文验证和执行路径保持原有目标版本检查。恢复所需的作者依赖索引准备移到后台线程，仍在验证计划依赖后才显示旧列表。
- 新增“启动窗口显示”诊断（GL4 可选 WS 字段）：从主窗体开始构造到 Shown，独立显示初始化/显示窗口阶段。旧日志没有此字段时显示“—”。首次列表可交互仍从相同起点计时，列表恢复耗时仍单独记录，不改变原指标含义。

验证：批量核对与托管枚举的递归/非递归名称一致，覆盖扩展名大小写、不匹配文件、空目录、取消、删除和改名；SDK 冷索引漏项补偿、范围监控隔离、元数据缓存复用和诊断历史兼容测试通过。真实 WinForms Everything 重启、增删改、校验期间变化、关闭取消和不可用源恢复测试通过；完整构建与四语言包通过（各 1,112 键，771 引用）。

本机 8,490 文件名核对：托管枚举 34 ms，批量枚举 20 ms（同进程顺序运行，文件系统缓存会影响该数字，不是严格冷盘对比）。真实窗口测试：首次扫描 4,081 ms；重启恢复 232 ms、窗口显示 237 ms、首次可交互 470 ms、完整性核对 19 ms、后台校验 1,071 ms；一次 Everything 查询，全部计划复用。测试库与实际库目录结构、介质不同，不能断言实际库的 1,122 ms 已缩短到 19 ms。此次交付替换独立测试程序，没有删除现有库缓存。

## 11:58 回退反馈后的修正（当前交付）

实际库出现完整性检查 3,575 ms、后台校验 4,755 ms 的回退；窗口显示 1,464 ms，列表恢复 377 ms，首次可交互 1,844 ms。这说明窗口显示前的工作是启动等待的主要部分；不能用本机小目录的大缓冲枚举结果推断实际库收益。

撤回 `FindFirstFileExW` 大缓冲原生枚举，恢复 Framework 托管目录枚举。保留名称集合直接核对、缺项立即回退、取消、错误时保留索引结果等一致性行为。删除启动测试中预先遍历全部测试文件的测速，以免它提前加热磁盘缓存影响启动样本。没有去掉完整性校验来换取表面速度。

审查还发现 `AuthorEntityStore.GetRecognitionVersion` 每次读取 JSON、解析、规范化、验证并序列化语义视图，而一个扫描请求会多次调用它。现在按原始文件内容 SHA-256 检查变化；未变化时复用已生成的两个语义指纹，变化时从同一份读取的字节重新生成。避免仅依赖文件时间和大小，也不缓存可变的作者实体对象。原指纹计算内容和相关作者失效语义保持不变。新增测试覆盖同大小且保留时间戳的外部编辑、仅相关指纹改变，以及损坏内容不得返回旧指纹。

主窗体构建界面期间暂停并合并 Form 布局；新增“启动初始化（设置 / 数据 / 缓存 / 界面）”四段计时，GL4 可选 SI 字段，旧记录缺失显示“—”。数据段包含数据存储与引擎准备，缓存段包含 SQLite 和缓存服务初始化，界面段包含控件构建、恢复设置和布局。窗口显示总耗时还包含构造函数尾部和实际 Show 阶段，四段不能替代窗口显示总指标。

验证：增量契约、指纹内容变化、真实 WinForms Everything 启动/增删改/关闭取消、统一作者库（包括精准失效和 5,000 实体中英德显示）、窗口导航回归通过；完整构建及四语言验证通过（1,113 键、772 引用）。本机测试库窗口显示 306 ms、恢复 237 ms、首次可交互 544 ms、完整性检查 25 ms、后台校验 1,051 ms；一次 Everything 查询，8,490 计划复用。此次尚未取得实际库复测，不能声称实际库 4,755 ms 或 1,464 ms 已降至这些数字。继续交付独立程序，无需删除缓存。
