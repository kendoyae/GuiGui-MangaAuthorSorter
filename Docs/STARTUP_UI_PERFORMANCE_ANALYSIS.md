# V1.13.0 启动 UI 性能分析：第一轮

日期：2026-10-09。本轮只增加测量和对照测试，不调整作者库指纹、枚举接口、缓存信任规则或主界面布局。生产默认仍为恢复缓存后立即调度校验；B/C 仅通过隔离测试程序的内部构造参数选择，不保存到用户设置，也不提供关闭安全校验的用户开关。

## 交付与测量口径

交付程序：`bin/Release/GuiGui.CacheRecovery.exe`。无需删除缓存。性能诊断“复制”包含完整启动明细，面板显示主要项目摘要。历史 GL4 追加可选 SU、DS、DN、DCM 字段；旧记录缺少字段时显示“—”，实际测出的 0 保留。没有变更缓存 schema。

所有启动时间点与区间使用主窗体同一个 Stopwatch。时间点从构造起点计时；区间可能嵌套，不能和父区间相加。未覆盖的耗时可用相邻时间点做差，而非累加所有阶段。

- 构造：界面初始化完成、构造完成；保留设置/数据/缓存/界面四段。
- 静态界面：图标/字体/DPI 设置、菜单、顶部控件、主体控件、表格样式、列、菜单和事件注册。
- 显示：首次 SetVisibleCore 起止、句柄创建完成、Load 起止、Shown 起点与处理区间、主窗体 Layout 累计区间、ResumeLayout。
- 绘制：窗口首次 Paint、表格首次 Paint、填入缓存后的表格 Paint。
- 恢复：上下文准备、工作线程起止、作者依赖准备、计划读取及逐行依赖校验、后台读取到 UI 继续执行的等待、应用结果、表格列宽和筛选。
- 响应：缓存表格 Paint 后，通过 BeginInvoke 记录 UI 消息响应时间点。它证明后续 UI 消息得到处理，没有注入真实按键；不把 Paint 事件等同于整帧像素呈现完成。
- 校验：调度时间点及 ScanPreview 返回前的主线程准备区间，和后台校验总耗时分开。

原“首次列表可交互”字段仍保留原口径：缓存填表方法返回时记录。新增“缓存绘制后消息响应”用于观察之后的绘制及消息等待，避免直接改变历史指标含义。

完整性检查只拆分名称集合准备、文件枚举与扩展名筛选、名称对比。仍使用原 Framework 枚举和全名称核对；未加入目录时间戳信任、USN Journal 或跳过验证机制。

## A/B/C 对照

测试数据为 8,490 个真实占位文件、1,169 个作者实体及作者目录，先成功扫描建立 SQLite 缓存。每次重启在独立进程中运行，使用同一份测试缓存；三轮按 ABC、BCA、CAB 轮换，降低顺序偏差。主窗体正常显示，进行绘制及消息响应观察。最后的正式三轮没有并行运行其他回归测试。

- A：保留现有行为，恢复缓存后立即调度校验。
- B：缓存已经绘制且 UI 处理了后续消息，再调度校验。
- C：不自动校验，单测启动恢复；缓存始终只读，整理按钮不可用。现有公共作者索引后台准备在三组中保持一致，因此该对照仅隔离文件校验，不排除其他后台工作的影响。

## 当前可以确认的热点

### 静态界面构建是主要部分

以 A 组中位数观察：控件初始化区间 581 ms，菜单 161 ms，顶部控件 74 ms，主体控件 210 ms；主体包含表格配置 122 ms。表格内部为样式 65 ms、列配置 42 ms、菜单/事件 9 ms。图标/字体/DPI 设置约 82 ms，恢复界面设置 17 ms，ResumeLayout 4 ms，主窗体 Layout 累计 3 ms。

这些区间有嵌套关系。它们表明本轮测试中主要成本在创建和配置静态界面，不能把约 614 ms 归因于加载 8,490 行。主窗体 Layout 累计不代表所有子容器的布局耗时；子布局仍包含在相应控件创建区间中。

现有主表已经设置 `VirtualMode=true`。本轮没有切换模式或重写列表状态管理。恢复表格的列宽处理约 0 ms，筛选/装入约 72 ms，整个恢复应用约 95 ms。暂未发现列宽全量测量是启动的主要热点。

### 构造完成到 Shown 的缺口主要在首次显示

例如正式 round-1-A：界面初始化完成 1,066 ms，构造完成 1,075 ms，首次显示开始 1,077 ms，句柄创建完成 1,083 ms，Load 开始 1,158 ms、结束 1,161 ms，首次显示返回 1,281 ms，Shown 为 1,286 ms。构造尾部约 9 ms，而首次显示区间为 203 ms。

因此这个测试中的主要未覆盖部分在首次显示、子控件/Load 前后，而不是构造函数末尾；Load 事件处理自身仅 2 ms。对于用户实际库的约 347 ms 缺口，需要用新版时间点做同样拆分，不能直接套用本机 203 ms。

### 即时校验增加了缓存绘制前的等待

三组窗口显示时间接近；代码中的文件校验在恢复缓存之后才启动，所以它不能解释窗口显示前的一秒多成本。A 组在缓存绘制前先执行了同步扫描准备，而 B 把这项工作移到已响应之后。A 的填表到绘制后响应间隔比 B/C 高约 64–68 ms。

该差异包含同步准备、消息调度和绘制，不能全部归因于后台目录枚举争用 CPU 或磁盘。把校验延后可能改善首次缓存呈现，但本轮未改变默认调度。

### 显示到缓存可交互的间隔还包含缓存读取

测试库恢复计划读取及逐行依赖校验约 695 ms，整个恢复等待约 698 ms；该区间包含读取、反序列化和逐行依赖验证，不是纯 SQLite I/O。测试库还包含作者实体和目录，不能直接对照用户实际库的 387 ms 恢复记录。

“Shown 到首次交互”的差值不能全部称作绘制阻塞。新版把缓存等待、结果应用、Paint 和消息响应分开，实际库的下一份日志可以进一步区分这些成本。

## 下一轮建议

1. 优先核对实际库的菜单、表格样式/列、字体/DPI 与首次显示时间点，再针对测出的静态界面热点优化。保留当前布局、VirtualMode 和状态逻辑。
2. 独立评估采用 B 调度，目标是让缓存先绘制并响应；保持未验证列表只读。预计收益主要在缓存呈现后的几十毫秒，不能承诺消除整个 1.85 秒。
3. 用完整性检查三段确认实际库是否仍以枚举为主。USN Journal 留到独立第三轮，必须先设计卷身份、日志连续性、覆盖及回退证明。本轮未实现或声称具备该能力。

## 验证与复现

三轮正式 A/B 中均保持 8,490 条计划复用、0 次实际识别、0 次计划写入、一次 Everything 查询。C 没有自动扫描，保持 8,490 条恢复记录只读。SDK 漏项补偿、增删改、规则失效、诊断历史兼容、关闭取消、不可用源恢复和窗口导航回归通过。四语言包验证通过：1,159 键、776 个静态引用；运行时实际出现的动态计时标签也有断言。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File Build/RUN_STARTUP_UI_EXPERIMENTS.ps1 -Rounds 3
cmd /c Build/RUN_INCREMENTAL_CONTRACT_TESTS.cmd
```

测试仅使用独立临时目录，不归档用户文件。结果是本机少量样本，并非实际库的性能承诺；不同介质、公共作者库、DPI、冷启动状态及测量代码开销都会影响绝对耗时。
